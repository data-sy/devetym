## 0. 라운드 0 — 프롬프트 §0 사실 정본의 정정

설계 착수 전 저장소를 실측했다. 프롬프트가 전제한 사실 중 **4건이 어긋났고**, 그중 2건은 설계를 바꾼다.

| # | 프롬프트의 전제 | 실측 | 영향 |
|---|---|---|---|
| 1 | 디자인 토큰이 `docs/design`에 있음 | **없음.** `docs/design/`엔 Android 아이콘 SVG 4종 + README뿐. 토큰 정본은 **코드** — `ui/theme/AppColors.kt`(라이트/다크 각 10색)·`AppTypography.kt`·`AppDimens.kt` | 토큰 상속이 "파일 복사"가 아니라 **코드에서 값 추출**. W0 작업 항목으로 승격 |
| 2 | 백엔드 경계 = ADR-0004 / ADR-0006 | ADR-0004는 **Superseded**(by 0006, 2026-07-05). 계약 정본은 **0006 단독** | 참조 오류 정정. `X-Device-Id`·429 계약은 0006이 계승 |
| 3 | 오류 계약 = 429 | **402 `service_exhausted` 추가됨**(2026-07-14). `ErrorKind` 6종 = Timeout·Network·InvalidResponse·DailyLimitExceeded·ServiceExhausted·Unknown | 웹도 3분기(200/429/402) + 6종 매핑 필요 |
| 4 | 전역 캡 부재 (§4가 지목한 위협) | **이미 구현돼 있음.** `devetym-proxy/src/index.js`: `DAILY_LIMIT = 10`(기기당) · `GLOBAL_DAILY_LIMIT = 200`(전체 합산). 주석이 목적을 명시 — *"X-Device-Id 위조로 기기 한도를 우회해도 하루 총 지출이 여기서 멈춘다"* | **페르소나 4의 전제가 바뀐다.** 헤더 위조 구멍은 방벽이 이미 있음. 남은 문제는 위조가 아니라 **표면 간 전이** |

**추가 실측 — §0에 없던 것**

- **캐시 히트는 한도 검사를 통과하지 않는다** (`src/index.js:141`, 비준 B4). D1에 있는 용어는 무과금·무한도로 서빙된다. → 웹의 캐시 읽기 경로는 **이미 존재한다**. 신규 엔드포인트 불필요.
- **CORS 헤더가 전혀 없다.** 브라우저는 현재 프록시를 호출할 수 없다. 웹 개방의 필수 최소 변경.
- 비용 방어선이 이미 가동 중: 조직 월 spend limit **$30** + $10/$20/$25 알림. 7월 실적 **$0.20**(예산 1%).
- `docs/cost/cost-management-decision.md`가 `X-Device-Id` 위조 가능성을 **이미 인지된 리스크로 기록**하고 있다. 이 설계가 새로 발견한 것이 아니다.

## 1. 콘텐츠 실측 — 이 설계의 모든 판정이 여기서 나온다

`terms.json`(650항목, 518KB)을 직접 집계했다. 두 숫자가 설계를 지배한다.

### 1-1. 검색 표면

| 항목 | 값 | 함의 |
|---|---|---|
| 엔트리 | 650 | |
| 고유 정규화 keyword | **650 (충돌 0)** | `/term/{slug}`가 **정확히 650개 고유 URL**을 만든다. 충돌 처리 불필요 |
| **한글 keyword** | **0** | 표제어는 전부 영어 |
| 고유 별칭 키(keyword와 별개) | 1,316 | |
| **그중 한글 별칭** | **1,097** | ← **이 설계에서 가장 중요한 숫자** |
| 총 검색 가능 키 | 1,966 | |
| 교차 충돌(다른 엔트리에 가려진 별칭) | 3 | `집계`→aggregate(aggregation 가려짐) · `분기`→branch(fork) · `샤딩`→shard(sharding) |

**한글 별칭 1,097개가 이 이행의 유입 자산 전부다.** 제품은 *한국어로 쓰인 영어 용어 사전*이다. 한국인은 구글에 `뮤텍스 어원`이라고 치지 `mutex etymology`라고 치지 않는다. 그런데 표제어는 전부 영어이고, 한국어 이름은 `aliases` 안에 들어 있다 — **현재 앱 구조에서는 검색 표면에 드러나지 않는 자리**다.

→ 웹 페이지가 한글 별칭을 title·h1·메타·구조화 데이터에 **1급 시민으로 노출하지 않으면, 650개 페이지는 한국어 검색에 대해 사실상 존재하지 않는다.**

### 3-1. 웹으로 넘겨야 할 "숨은 규칙" — 코드에 없으면 조용히 깨지는 것들

1. **`normalizeKeyword(s) = s.trim().lowercase()`는 키잉 전용이다.** AI에 보내는 질의에는 **원본 대소문자를 보존**한다. `AppJson.kt`의 주석이 이유를 명시: lowercase가 `NaN`·`Go`·`REST`·`C`의 의미를 뭉개 **어원 오답**을 유발한다. 이걸 어기면 실패가 크래시가 아니라 *조용히 틀린 콘텐츠*로 나타난다.

2. **⚠️ Kotlin `trim()` ≠ JavaScript `trim()`** — 공백 문자 집합이 다르다. `AppJson.kt` 주석이 이미 이 함정을 경고하고 있고, **프록시에 `normalizeTermKey`라는 JS 복제본이 이미 존재한다**(`devetym-proxy/src/index.js`). 웹이 세 번째 구현을 만들면 드리프트 지점이 3개가 된다.
   → **결정: 프록시의 JS 구현을 공유 패키지로 뽑아 웹이 import한다.** JS 쪽 정본은 1개로 유지된다. 동치 검증 정본은 `shared/src/commonTest/.../NormalizeKeywordTest.kt`(2026-08-04 커밋 `e9cd0b2`에서 정비됨)이며, 그 케이스를 JS 쪽에 미러링한다.
   → 어긋나면 **캐시 미스로는 드러나지 않는다** — 서버는 자기 일관적이므로. 번들 승격 잡이 흘린 키를 클라가 영영 조회 못 하는 형태로 샌다.

3. **번들 인덱스는 keyword + 모든 aliases를 정규화해 접고, 충돌 시 first-wins.** 실측 교차 충돌 3건(집계·분기·샤딩)에서 뒤 엔트리가 검색에서 가려진다.
   → **웹은 이 결함을 구조적으로 고친다.** 정적 페이지는 용어마다 자기 URL을 가지므로 `aggregation`도 페이지를 갖는다. 검색창만 first-wins를 따르면 되고, 웹에서는 오히려 "두 결과 다 보여주기"가 자연스럽다.

4. **`autocomplete`는 keyword prefix만 보고 aliases를 제외한다** (`BundleDbSource` 명세). → D7에 따라 **웹은 의도적으로 갈라진다.** 앱 명세를 그대로 옮기면 한글 입력에 자동완성이 전혀 반응하지 않는다.

5. **`aliases` 키가 이름이 다르거나 생략되면 예외 없이 `emptyList()`로 떨어진다** (INV-A). 성공 디코드로는 안 잡힌다. → 웹 빌드에도 **실제 `terms.json`으로 별칭 보존을 단언하는 검증**을 넣는다.

6. **category clamp**: 6집합(동시성·자료구조·네트워크·DB·패턴·기타) 밖이면 `기타`로 접는다. **AI 경로에만** 적용하고 번들·캐시 경로는 clamp하지 않는다.

7. **`TermResult`는 3분기다**: `Found` · `NotDevTerm` · **`PossibleTypo(suggestion)`**. 오타 제안 분기를 웹 UI가 빠뜨리기 쉽다.

8. **저장 안 하는 분기**: `NotDevTerm`·`PossibleTypo`는 히스토리도 term도 저장하지 않는다(lazy). 웹에서도 이 규칙이 D1 오염 방지에 직결(§4-1 T5).

9. 타임아웃 30초 · 디바운스 300ms · 최근검색 5개.

10. **단일-writer 직렬화(DR-2)** — 정규화 키로 키잉된 Mutex. 웹 v1은 로컬 저장이 없어 RMW가 없으므로 **불필요**. 개인화를 추가하는 순간 부활한다.

### 4-2. 채택안과 기각안

**채택 — 4겹 방어**

1. **Turnstile** — 웹의 *생성* 요청에 토큰 필수. Worker가 siteverify 후 통과. 정적 페이지 열람·캐시 히트에는 요구하지 않는다(유입 마찰 0).
2. **표면 분리 캡** — 웹 요청과 앱 요청을 구분해 **웹 전용 전역 캡**을 앱 캡과 별도로 둔다. 웹이 자기 몫을 다 태워도 앱 몫 200은 그대로 남는다. ← T2/T3 전이 차단의 핵심.
3. **IP 기반 한도** — `CF-Connecting-IP`는 Worker가 직접 보는 값으로 **클라이언트가 위조할 수 없다.** Turnstile 우회분을 잡는다. CF 무료 플랜의 rate limiting rule 1개를 여기에 쓴다.
4. **Anthropic 워크스페이스 분리 + 워크스페이스별 spend limit** — `cost-management-decision.md`가 "원리 1"로 이미 제안해 두고 미적용(조직 단위만 적용)인 항목. **이제 적용할 트리거가 발생했다.** 웹이 태워도 앱 워크스페이스 예산은 살아 있다.

**기각**

- *웹 차단 / 캐시 읽기 전용* — 사람 결정(D5)으로 기각. 덧붙여 실측상 D1 누적 생성량이 수십 건 미만으로 추정돼(7월 $0.20 기준) 캐시 읽기 전용은 실질적으로 "차단"과 같다.
- *계정 + 쿼터* — 유입에 마찰이고 D10(개인화 제외)과 불일치.
- *현행 `X-Device-Id` 그대로 웹 개방* — 브라우저에서 자유 위조 + 전이 위험. 기각.

### 4-3. `devetym-proxy` 변경 범위와 INV-1 저촉 검토

| 변경 | 앱 영향 | INV-1(앱 코드 무변경) |
|---|---|---|
| CORS 헤더 추가 (고정 allowlist, 동적 에코 금지) | 없음 | **유지** |
| Turnstile 검증 (웹 요청에만) | 없음 | **유지** |
| 표면별 캡 분리 | 앱 캡은 현행 200 유지 | **유지** |
| 워크스페이스 분리 | 서버 키 교체만 | **유지** |
| 프롬프트 이전(D8) | 앱은 계속 자기 프롬프트를 보냄 → 서버가 무시하거나 우선 적용 | **유지 가능하나 검증 필요** |

**⚠️ 미해결 충돌 — 정직하게 기록한다.**
표면 구분을 `Origin` 헤더 + Turnstile 토큰 유무로 하면, **브라우저는 `Origin`을 위조할 수 없지만 `curl`은 아예 보내지 않거나 위조할 수 있다.** 즉 공격자가 "앱"으로 위장해 앱 몫 캡(200)을 먹는 경로가 남는다. 이걸 완전히 막으려면 앱 요청에도 검증 가능한 서명이 필요하고, **그건 INV-1을 깬다.**

→ **조정자 판정**: 부분 격리를 수용한다. 근거는 *웹 개방이 이 경로를 악화시키지 않는다*는 점이다 — curl 위장은 지금도 가능하고, 지금도 200에서 막힌다. 완전 격리는 **다음 앱 릴리즈에서 앱 측 서명을 도입할 때** 해결하고, 그때까지는 워크스페이스 spend limit(4겹 중 4번)이 최종 안전망을 맡는다.

### 4-5. 캡 설정값 — 예산 역산과 그 해석 (2026-08-05 사람 확인 반영)

월 예산 $30 중 웹에 약 $20~27을 배정하면 **하루 22~30건**이 상한이다. **이 수는 전체 방문자 합산이며, "방문 수"가 아니라 "아무도 물어본 적 없는 새 단어"의 수다.** 번들 650개와 D1 캐시 히트는 이 수에 들어가지 않는다.

| 방문자 1인당 평균 신규 단어 검색 | 하루 22건이 감당하는 방문자 |
|---|---|
| 0.5건 (초기 — 캐시가 얇을 때) | 약 44명/일 |
| 0.1건 | 약 220명/일 |
| 0.05건 (캐시 축적 후) | 약 440명/일 |

**미스율은 시간이 갈수록 단조 감소한다**(write-once 동결 + 번들 승격 플라이휠, INV-12). 신생 사이트의 첫 몇 달은 현 예산으로 감당 가능하다.

**⚠️ 진짜 취약점은 평균 트래픽이 아니라 집중이다.** 현행 1인당 한도 10건 × 전체 캡 22건이면 **의욕적인 3명이 하루 몫을 소진**하고 나머지 방문자는 종일 429를 본다. 익명 웹 방문자에게 앱과 같은 10건은 전체 캡 대비 과대하다.

**채택 설정값 (W1a) — 웹은 3층 분리**

⚠️ **웹에 단일 "1인당 한도"를 두면 안 되는 이유**: 웹에는 앱의 `X-Device-Id`에 해당하는 것이 없고, 위조 불가능한 식별자는 IP뿐이다. 그런데 **한국 모바일 통신사는 CGNAT을 광범위하게 쓴다** — 다수 사용자가 같은 공인 IP를 공유한다. IP당 3건으로 걸면 모바일 유입 사용자들이 서로의 몫을 잠식한다. 검색 유입은 모바일 비중이 높으므로 실질적 위험이다.

| 층 | 기준 | 값 | 성격 |
|---|---|---|---|
| **사용자 대면** | 브라우저(쿠키/localStorage) | **3건/일** | UX 한도 + **앱 유도 전환점**. 리셋 가능하나 아래 층이 받친다 — **의도된 느슨함** |
| **남용 방지** | IP (`CF-Connecting-IP`, 위조 불가) | **15건/일** | CGNAT 공유를 감안한 백스톱. 브라우저 한도를 리셋해가며 쓰는 경로를 여기서 막는다 |
| **예산** | 웹 전역 | **30건/일** | 비용 상한. 10명이 각자 3건을 다 써야 소진 |
| 앱 전역 캡 | 앱 표면 | **200건/일 (현행 유지)** | 예산 상한이 아니라 **폭주 차단 회로차단기** — 다 쓰면 월 $180으로 예산과 불정합. 실제 예산 강제는 Anthropic spend limit이 맡는다 |
| 앱 1인당 한도 | 기기 | **10건/일 (현행 유지)** | 설치까지 한 사용자 |

**⚠️ 문구에서 반드시 구분할 것**: 3건은 **AI 신규 생성** 3건이지 *페이지 열람* 3건이 아니다. 번들 650개와 D1 캐시 히트는 무제한이며 한도 검사조차 통과하지 않는다(비준 B4). 이 구분을 UI가 흐리면 "3페이지 보면 막히는 사이트"로 오해받는다 → **Q4**.

**예산은 $30 유지로 시작한다.** 상향이 필요해지는 상황은 나쁜 신호가 아니라 **유입이 붙었다는 신호**이며, 그때 $50~$100이 정당화된다. 선제 상향은 하지 않는다.

### 4-6. 3건 한도가 만드는 전환 경로 — 그리고 그 대가

**설계상의 빈 자리를 메운다.** 페르소나 1은 "유입 이후 전환 경로"를 판정 항목으로 요구했으나, 최초 판정은 *"앱 설치는 귀속 측정이 어려워 KPI로 삼지 않는다"* 였다 — 사실상 **전환 경로가 없다**는 뜻이었다. 3건 한도 + 앱 유도가 그 경로를 만들고, 동시에 **측정 가능하게** 만든다(한도 화면 도달 → 앱 링크 클릭률). 이는 채널 확장(c) 전략을 한도로 물리 구현한 것이다.

**걸리는 사용자는 소수다.** 검색 유입 방문자 대다수는 착지 페이지 하나만 보고 이탈한다. 번들에 없는 단어를 3회 이상 찾는 방문자는 이미 적극 사용자이며 앱 설치 후보와 정확히 겹친다.

**⚠️ 정직하게 기록하는 대가 — D5 논거의 부분 후퇴.**
사람이 A안을 고른 근거는 *"AI로 원하는 어원을 다 설명해준다가 제품 정체이며 그것이 없으면 의미가 없다"* 였다. 웹에 3건 벽을 세우면 **웹은 "다 설명해준다"를 제공하지 않고 "3개까지 증명해 보인다"를 제공한다.**

→ **조정자 판정**: 수용한다. 웹 = 능력을 **증명하는** 표면, 앱 = 능력을 **무제한 제공하는** 표면으로 역할을 분담한다. 3건은 증명에 충분하다(1건은 우연으로 읽히고, 3건이면 "무엇을 물어도 된다"가 전달된다).
→ 단, 이 결정은 **A안과 B안 사이에 착지한다는 점을 명시한다.** AI를 W1에 열되 웹에서는 맛보기로 여는 형태다. 비용·전환 양쪽에서 순수 A안보다 우수하나, "첫인상에 완전한 제품을 보여준다"는 A안의 논거 일부를 스스로 되돌린다. **이 교환은 사람이 인지한 상태에서 채택되었다(2026-08-05).**

### 5-1. URL·메타데이터 방침

| 항목 | 결정 |
|---|---|
| 용어 상세 | `/term/{slug}` — slug = `normalizeKeyword` 결과의 URL-safe 변환(공백→`-`). **650개 고유, 충돌 0** |
| 카테고리 허브 | `/category/{6종}` — 얇은 콘텐츠 완화 + 내부 링크 구조 |

| **title/h1** | **한글 별칭을 1급으로.** 예: `뮤텍스(mutex) — 왜 이렇게 부르는가` |
| 구조화 데이터 | `DefinedTerm` + `DefinedTermSet`. `alternateName`에 **한글 별칭 전부** |
| `site/`(Jekyll)와의 관계 | 충돌 없음(privacy/terms만 존재) |
| **도메인** | **`devetym.com` — 이름 확정(2026-08-05).** 구매·DNS 연결은 W0. 다운스트림 3곳은 아래 **순서 게이트**를 따른다 |

**⚠️ 다운스트림 3곳 — 이름 확정만으로 바꾸지 않는다** (어긋나면 스토어 심사 항목에 걸린다):
1. `Constants.kt`의 `privacyPolicyUrl` — 현재 `https://data-sy.github.io/devetym/privacy-policy`
2. App Store 스토어 메타의 개인정보 처리방침 라벨
3. `site/`(Jekyll) 정책 페이지의 게시 위치

**순서 게이트(W0)**: ① `devetym.com` 구매 → ② 정책 페이지를 새 도메인에 실제 게시하고 200 응답 확인 → ③ `Constants.kt` 교체 → ④ 스토어 라벨 갱신. **역순 금지** — 1의 값은 이미 App Store에 게시된 앱이 여는 라이브 URL이고 스토어 메타 라벨과 일치해야 하므로, 페이지가 서기 전에 상수를 옮기면 게시본이 죽은 URL을 가리킨다. 이름이 정해졌다는 사실과 URL을 옮겨도 되는 시점은 다르다.

**가용성 실측(2026-08-05)**: `devetym.com` = whois `No match for domain "DEVETYM.COM"` → **미등록, 채택 확정**. `devetym.io` = `whois.nic.io` "Domain not found" → 미등록. `.app`/`.dev` = NS 레코드 없음(미등록 유력, 레지스트리 whois는 조회 환경 제약으로 미확인) — 채택하지 않음.

참고: `Constants.kt` 주석에 *"종전 `SettingsScreen` 하드코딩(`devetym.app` — 미보유 도메인 플레이스홀더)"* 기록이 있다. 과거 상정 이름은 `.app`이었으나 채택은 `.com`이므로, ③ 단계에서 이 주석의 플레이스홀더 서술도 함께 정리한다.

### 6-1. "이 이행을 하지 않는 것"이 더 나은가 — 진지한 검토

**부분적으로 그렇다. 그리고 그 부분이 결정 D2를 바꿨다.**

- 순수 SEO 목적이라면 **기존 `site/`(Jekyll)를 650페이지로 키우는 것으로 충분하다.** React는 불필요하다.
- 그러나 사람이 A안을 고른 근거 — *"AI로 원하는 어원을 다 설명해준다가 제품의 핵심"* — 는 정적 Jekyll로 달성할 수 없다. 동적 호출·상태·Turnstile 위젯이 필요하다.
- **따라서 이행은 정당화된다. 다만 "React 웹앱"이라는 표현은 과잉이다.** 실제로 필요한 것은 **정적 사이트 650페이지 + 인터랙티브 섬 하나(검색 + AI 폴백)**다.
- → 이것이 D2에서 Next.js·Remix·Vite SPA를 기각하고 **Astro + React 아일랜드**를 채택한 이유다. 사용자의 "리액트" 요구는 섬 안에서 충족되고, 나머지 649페이지는 JS를 싣지 않는다.

**페르소나 6의 결론: 이행하라. 단 사용자가 말한 형태가 아니라 위 형태로.**

| **H1** | `devetym.com` 구매 — **Cloudflare Registrar** (2026-08-05 확정) | 도메인이 CF 계정 DNS 아래 | W0 전부 |
| **H2** | Workers 배포용 API 토큰 발급 | `CLOUDFLARE_API_TOKEN` 환경변수 | 자율 배포 · 전수 URL 오라클 |
| **H3** | Search Console 소유권 확인 (**DNS TXT** — 사이트 배포 불요) | 확인 완료 상태 | K1 측정 |

**등록기관 선택 근거(H1)**: Cloudflare Registrar는 프록시·D1·KV와 같은 계정이라 DNS·Workers 커스텀 도메인 연결이 추가 절차 없이 끝나고 마크업이 없다. 타 등록기관을 쓰면 **네임서버 이전 + 전파 대기**가 H1에 붙어 자율주행 착수가 밀린다.

**배치 범위(2026-08-05 사람 결정)**: H1~H8을 **한 번에** 처리한다. W0 끝에서 멈춰 W1a 자격증명을 나중에 준비하는 안은 기각 — 무인 관통 구간을 W0→W1a→W1b로 길게 가져가는 편이 이 트랙의 목적에 맞는다.

**⚠️ H7은 계정 작업이 아니라서 눈에 띄지 않지만 규율상 가장 단단한 게이트다.** ROADMAP이 *"비준은 사람 승인 후 — 거버넌스·데이터면 자동 수정 금지"* 를 못박아 두었으므로, 비준 없이 자율주행이 W1a를 실행하면 **아직 `Proposed`인 ADR-0010·0011을 구현하는 것**이 된다.

### 9-2. W0 DoD 정정 — 두 개로 쪼갠다

§5-5의 W0 DoD(*"빈 사이트가 실 도메인에 배포되고 Search Console이 소유권을 확인"*)는 **순서를 과하게 묶어 사람을 두 번 부른다.** 소유권 확인은 DNS TXT로 되므로 사이트 배포를 기다릴 필요가 없다. 묶어두면 사람이 (구매 → 자율주행 배포 대기 → 재로그인 확인)으로 두 번 불려나온다.

| W0-a | Search Console 소유권 확인됨 | **사람(H3)** — H1 직후 같은 자리에서 |
| W0-b | 빈 사이트가 `devetym.com`에 배포되고 200 응답 | **자율주행** |

### 9-4. X4 해결 — 표면 판정과 키 선택 규칙 (2026-08-05)

**먼저 두 판정을 쪼갠다.** 설계서는 이 둘을 한 덩어리로 다뤘으나, **틀렸을 때의 대가가 다르므로 별개로 적어야 한다.**

| 판정 | 틀리면 | 심각도 |
|---|---|---|
| (a) 어느 **캡**을 소모하는가 (웹 30 / 앱 200) | 캡이 엉뚱한 쪽에서 닳는다 → T2 재현 | 중 — 회복 가능(다음 날 리셋) |
| (b) 어느 **워크스페이스 키**로 과금하는가 | 웹 트래픽이 **앱 예산**을 태워 앱이 402로 정지 | **최상 — 이것이 F5다** |

**판정 축은 `Origin` 헤더 하나뿐이다.** 근거: **브라우저는 교차 출처 요청에서 `Origin`을 생략할 수 없다**(스펙 강제). 반대로 네이티브 HTTP 클라이언트는 붙이지 않는다. 즉 `Origin`의 **존재**는 위조 가능하지만 **부재**는 브라우저가 만들 수 없다 — 이 비대칭이 유일하게 쓸 수 있는 신호다.

| # | `Origin` | Turnstile | 실체 | 판정 |
|---|---|---|---|---|
| 1 | `devetym.com` | 유효 | 진짜 웹 | **웹 캡 + 웹 키** |
| 2 | `devetym.com` | 없음/무효 | 봇 또는 우회 시도 | **차단** (단 캐시 히트는 통과 — 무과금) |
| 3 | allowlist 밖 | — | 제3자 사이트 (T4) | **차단** (키 선택 이전) |
| 4 | 없음 | — | 진짜 앱 | **앱 캡 + 앱 키** |
| 5 | 없음 | — | `curl` 앱 위장 | 앱 캡 + 앱 키 **(구분 불가 — 아래)** |

**규칙**: `Origin`이 allowlist에 있으면 **웹**, 없으면(헤더 부재) **앱**, allowlist 밖이면 **차단**. 웹 키는 **fallback이 아니라 명시적 조건**이다.

**검사 순서** (기존 코드의 캐시-우선 규율을 계승):
`Origin` allowlist 검사 → 본문 파싱 → **캐시 조회**(히트면 여기서 끝 — 캡·키·Turnstile 전부 무관, 비준 B4) → 표면 판정 → Turnstile 검증(웹만) → 캡 3층 검사 → **키 선택** → Anthropic 호출.

**캡 3층 검사 순서는 사용자 대면 → IP → 전역**이다. 셋 다 통과해야 하므로 순서가 통과 여부를 바꾸지는 않지만 **어떤 오류를 돌려주느냐가 달라진다.** 3건을 다 쓴 사람에게는 "앱에서 무제한" 안내(Q4의 전환 지점)가, IP·전역에 걸린 사람에게는 다른 문구가 나가야 한다.

**⚠️ 잔여 리스크 — 정직하게 기록한다.** 케이스 5(`Origin` 없는 `curl` 위장)는 케이스 4와 **구분할 수 없고, 따라서 앱 예산 쪽으로 샌다.** INV-1(앱 무변경) 하에서는 앱 요청에 검증 가능한 서명을 붙일 수 없으므로 이 구멍은 닫히지 않는다.
→ **판정: 수용한다.** §4-3 조정자 판정과 같은 근거다 — *웹 개방이 이 경로를 악화시키지 않는다.* `curl` 위장은 지금도 가능하고 지금도 앱 전역 캡 200에서 멈춘다. 웹 개방이 새로 만드는 것은 **`Origin`이 붙은 요청**뿐이고 그건 확실히 웹 쪽으로 분류된다. 최종 안전망은 **앱 워크스페이스의 spend limit**이며, 이것이 §4-2 4겹 중 4번째가 존재하는 이유다.

**부수 효과 — KV 쓰기가 3배가 된다.** 웹은 3층(브라우저·IP·전역) 각각에 카운터를 쓰므로 생성 1건당 KV 쓰기 3회다. 웹 30 × 3 + 앱 200 × 1 = **약 290회/일**, 무료 한도 1,000회/일의 **29%**. 여유 안이지만 **KV 쓰기는 우리가 무료 한도에 가장 가까운 항목**이므로(다른 항목은 전부 1% 미만) 캡 상향 시 여기가 먼저 걸린다는 것을 기록해 둔다.

**H5가 이 규칙으로 확정된다**: 사람은 **웹 전용 워크스페이스**를 새로 만들고 거기에 spend limit을 건 뒤 키를 `ANTHROPIC_API_KEY_WEB`으로 주입한다. **기존 `ANTHROPIC_API_KEY`(앱)는 건드리지 않는다** — 앱 쪽 키를 교체하면 게시된 앱의 라이브 경로를 만지는 것이 되므로 INV-1 정신에 반한다.

### 9-5. X2 해결 — 배포 오라클 지그 (2026-08-05)

F6이 *"배포된 실 URL 650개 전수 확인"* 을 오라클로 못박았으므로, **그것을 실행하는 지그가 산출물**이다. 위치 `web/scripts/verify-deployment.mjs`, 입력은 배포된 base URL.

**기대 URL 목록**은 `terms.json`에서 생성한다(650 slug + 카테고리 허브 6 + 고정 페이지). 사이트가 스스로 신고한 목록이 아니라 **콘텐츠 정본에서 독립적으로 도출**해야 오라클이 성립한다.

| 검사 | 단언 | 왜 |
|---|---|---|
| **A. 도달성** | 기대 URL 전수 GET → **200, 실패 0건** | F6 본체. 650 GET은 CF 무료 한도(100k/일)의 0.65% |
| **B. 색인 가능성** | `robots.txt`가 `/term/*`를 막지 않음 · `sitemap.xml`과 기대 목록의 **대칭차 0** · `/search`는 `noindex` · 그 외 페이지에 `noindex`가 **잘못 박히지 않음(전수)** | F6이 지목한 실패 형태가 *"robots 오설정·사이트맵 404"*. 대칭차를 봐야 양방향(사이트맵에만 있는 죽은 URL / 페이지는 있는데 미제출)을 다 잡는다 |
| **C. 유입 가설** | **한글 별칭이 렌더된 HTML의 `title`·`h1`·구조화 데이터 `alternateName`에 실제로 들어갔는지 — 전수** | **신규 추가.** §1-1이 *"한글 별칭을 1급으로 올리지 않으면 650페이지는 한국어 검색에 존재하지 않는다"* 고 판정했다. 이게 빠져도 **빌드는 성공하고 A·B도 통과한다** — INV-A(별칭 키가 다르면 조용히 `emptyList()`)와 정확히 같은 종류의 침묵 실패다. 도달성만 재는 오라클은 이 이행의 **1차 목적이 달성됐는지를 못 잰다** |

**판정**: 세 검사 전부 실패 0건 = W1b DoD. **Search Console 실측(K1)은 이 지그의 범위 밖**이다 — 사람 계정·API 자격이 필요하므로 H3 이후의 측정 활동으로 분리한다. 지그는 *배포가 옳게 됐는가*까지만 답하고, *색인이 됐는가*는 답하지 않는다.

### 9-6. X3 해결 — 골든 케이스 러너와 CI 축 (2026-08-05)

**러너 = vitest.** 근거: `devetym-proxy`가 이미 vitest 4 + `@cloudflare/vitest-pool-workers`로 돌고 있다(`test/` 7파일). 웹도 vitest면 **JS 쪽 러너가 하나로 유지**되고 Vite/Astro 생태계 기본과도 맞는다. 위치 `web/test/*.test.js`.

**CI 축은 프록시의 S축1~4 관용을 계승**한다:

| 축 | 내용 | 오라클 |
|---|---|---|
| W축1 정적 | 타입체크 · lint | 문법·타입 |
| W축2 단위 | **G1~G6** | 앱과의 등가 |
| W축3 빌드 | `astro build` + **650 산출 개수 단언** | 빌드 산출 |
| W축4 라이브 | 배포 후 **§9-5 지그** | **F6 오라클 — 이것만이 완료 판정** |

**G1의 처리 — 설계서 §3-1 2번을 실측에 맞게 개정한다.**

§3-1은 *"프록시의 JS 구현을 공유 패키지로 뽑아 웹이 import한다"* 고 적었으나, **두 repo가 분리돼 있어**(`~/devetym` / `~/devetym-proxy`) 그러려면 4줄 함수를 npm publish해야 한다 — 비용이 목적에 비해 과하다. 실측된 상태는 이미 더 낫다:

- `NormalizeKeywordTest.kt`는 **U+0000~U+FFFF 전수 실측 코드포인트 표**(JVM·iosSimulatorArm64 양축, 2026-07-27)이며 자기 문서가 *"클라-서버 term-key 동치의 정본"* 임을 선언한다.
- 프록시에 **짝 테스트 `test/term-key.test.js`가 이미 존재**하고, `normalizeTermKey`는 이미 `export`돼 있다.
- 즉 **Kotlin↔JS 게이트는 이미 서 있다.** 웹이 더하는 것은 *세 번째 구현*이 아니라 *두 번째 JS 소비자*다.

→ **채택: 웹은 프록시의 `normalizeTermKey`를 vendoring하고, W축1이 원본 파일과의 동일성을 단언한다.** 깨지기 쉬운 부분은 함수 본문이 아니라 `WS` 문자 집합 문자열이므로, 파일 동일성 검사가 가장 싸면서 정확한 게이트다. 드리프트가 **빌드 실패로 즉시 드러나** F7의 *"조용히 샌다"* 가 성립하지 않게 된다.
→ **기각(무거운 대안)**: 케이스 표를 JSON 정본으로 뽑아 Kotlin·프록시·웹 셋이 읽게 하는 안. 수동 규율을 완전히 제거하지만 **`NormalizeKeywordTest.kt`(정본 선언 파일)를 고쳐야 한다.** 지금 얻는 것 대비 건드리는 것이 크다 — 네 번째 소비자가 생기면 그때 재론한다.

| G5 | `ErrorKind` | 6종 × 한글 메시지 전수. **`else` 없이** — 종류가 늘면 빌드가 깨지도록 |

**추가 실측(2026-08-05)**: 카테고리 6집합이 이미 손으로 복제돼 있다 — `devetym-proxy/src/index.js:60` 주석이 *"devetym shared의 `Category.CANONICAL`과 동일"* 이라고 적는다. `normalizeKeyword`(F7)에 이어 **같은 드리프트 패턴의 두 번째 사례**이며, Q5 해결(프롬프트 서버 이전)이 도구 스키마를 서버로 옮기면서 이 복제도 함께 정리한다.
