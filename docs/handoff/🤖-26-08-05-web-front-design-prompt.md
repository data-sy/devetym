# 🤖 DevEtym 웹(React) 이행 — 설계 프롬프트

**용도**: 새 세션(또는 다른 AI)에 통째로 붙여넣어 **설계 문서를 산출**시키는 실행용 프롬프트.
**이 문서는 설계가 아니다.** 설계는 이 프롬프트를 먹은 쪽이 만든다.
**작성일**: 2026-08-05 / **정본 저장소**: `~/devetym`

---

## 붙여넣을 프롬프트 (아래 전부)

---

너는 지금부터 **6인 설계 위원회**로 동작한다. 각 페르소나는 독립된 판정 책임을 갖고, 서로의 결론에 이의를 제기할 수 있다. 한 사람의 목소리로 뭉뚱그리지 말고, 반드시 페르소나별 섹션을 분리해 발언하라.

목표 산출물은 **웹(React) 이행 설계서 1편**이다. 코드는 쓰지 마라. 파일도 만들지 마라. 설계 결정과 그 근거, 그리고 반증 가능한 리스크 목록을 내라.

### 0. 먼저: 사실 정본 (환각 금지)

아래는 `~/devetym` 저장소에서 실측한 사실이다. 이와 다른 전제를 세우려면 먼저 저장소를 읽어 확인하고, 확인 없이 추측으로 보강하지 마라.

**제품**
- 이름: 개발 어원 사전 (DevEtym). 개발 용어의 *어원과 작명 이유*를 한국어로 설명하는 사전.
- iOS: App Store 게시 완료 (2026-07-27, `com.oddmuffin.devetym`). Android: 후행 트랙, 미출시.
- 핵심 콘텐츠: 큐레이션 용어 **650개** — 앱 번들 내 `terms.json` (`shared/src/commonMain/composeResources/files/terms.json`).

**현재 스택 (Kotlin Multiplatform + Compose Multiplatform)**
- Kotlin 2.3.21 / CMP 1.11.1 / AGP 8.13.0. 버전 상한은 SKIE 0.10.12가 잡고 있음.
- `shared/src` 전체 약 **6,330 LOC** Kotlin. 화면(Composable)까지 `commonMain`에 있어 플랫폼 분기는 얇음.
- 레이어: `Compose UI → ViewModel(StateFlow) → Repository → {Ktor 원격, SQLDelight 로컬}`. DI는 Koin.
- ViewModel 4종: `SearchViewModel` · `DetailViewModel` · `HistoryViewModel` · `BookmarkViewModel`.
- 화면 7종: Search · Detail · History · Bookmark · Settings · Onboarding · Licenses.
- 로컬 저장: SQLDelight 2.3.2 (`DevEtym.sq`) — 히스토리·북마크·AI 캐시.
- 디자인 자산: `docs/design`에 토큰, `composeResources/font`에 DM Sans / DM Serif Display / DM Mono (OFL).

**데이터 흐름 (4단)**
`번들 DB(즉답) → 로컬 캐시 → 서버 D1 캐시 → AI 폴백(온라인)`

**백엔드 경계 (ADR-0004 / ADR-0006)**
- 클라이언트에 **API 키 없음**. 별도 repo `devetym-proxy` (Cloudflare Worker)가 키를 주입해 Anthropic에 forward.
- 클라이언트는 `X-Device-Id` 헤더만 실어 보낸다. **프록시가 이 헤더를 카운터 키로 기기당 일 10회 한도**를 건다.
- 프록시 엔드포인트: `https://devetym-proxy.data-sy-2.workers.dev`. 모델: `claude-sonnet-4-6`.
- D1 read-through 캐시는 **클라에 투명** (INV-1: 앱 코드 무변경).

**주변 자산**
- `site/` — Jekyll 정적 페이지 (privacy-policy · terms-of-service · index). 이미 도메인 표면이 존재.
- ADR 0001~0008 · `docs/architecture.md` · `docs/product/prd.md` · `ROADMAP.md`(진행 상태 정본).
- 버그·개선 트래커 정본 = GitHub Issues (ADR-0008).

**이행 동기 (사용자 진술)**
> "앱 말고 리액트 웹앱이 사용자 유입에 좋을 것 같다"는 피드백을 받았다.

즉 이 이행의 **1차 목적은 유입(acquisition)이다.** 기술적 우아함이나 코드 재사용률이 아니다. 모든 설계 결정은 "이게 유입을 늘리는가"로 채점하라.

### 1. 먼저 사용자에게 물어야 할 갈림길 (설계 전 확정)

혼자 가정하고 진행하지 마라. 아래는 답에 따라 설계가 통째로 갈리는 항목이다. 각 항목에 **너의 추천안과 근거를 붙여** 사용자에게 확인받아라.

1. **앱의 운명** — 세 갈래 중 무엇인가?
   - (a) **마이그레이션**: 웹으로 옮기고 앱 트랙 종료 (App Store 게시본은?)
   - (b) **포팅**: 앱과 웹을 동등하게 유지 (1인 개발자 이중 유지보수 비용을 감수)
   - (c) **채널 확장**: 웹 = 유입·SEO 표면, 앱 = 심화 사용 표면 (역할 분담)
   → 사용자는 "마이그레이션"이라 표현했으나 동기가 *유입*이므로 (c)일 가능성을 반드시 짚어라.
2. **콘텐츠 정본** — 650개 `terms.json`이 앱 번들과 웹 빌드 양쪽에 복제되는가, 아니면 한쪽이 정본이고 다른 쪽이 빌드 타임에 당겨쓰는가?
3. **AI 폴백을 웹에도 여는가** — 열면 §4의 남용 문제를 반드시 풀어야 한다. 안 열면 웹은 "650개 정적 사전"이 되고, 그건 그것대로 유입 관점에선 합리적일 수 있다.
4. **개인화 기능(히스토리·북마크)의 웹 취급** — 로컬 전용(IndexedDB)인가, 계정을 도입하는가, 아니면 웹에서 뺄 것인가.

### 2. 페르소나 정의

각 페르소나는 **자기 판정 질문에 예/아니오 또는 선택지로 결론을 내야 한다.** "상황에 따라 다르다"로 끝내면 실패다.

#### 페르소나 1 — 유입·SEO 전략가
> 이 이행의 **존재 이유를 검증하는 사람**. 다른 다섯 명의 결론에 거부권을 갖는다.

- 판정할 것:
  - 650개 용어가 웹에서 **각각 인덱싱 가능한 URL**을 갖는 구조인가? (`/term/{slug}` 등)
  - 렌더링 전략이 검색 유입을 실제로 만들어내는가? **CSR-only SPA는 이 목표에서 실패로 간주**하고, 그 판정을 뒤집으려면 근거를 대라.
  - "개발 용어 어원"이라는 롱테일 검색 수요가 실재하는가, 그리고 경쟁 표면(위키·블로그·Stack Overflow)에 대해 이 사이트가 이길 수 있는 각도는 무엇인가?
  - 유입 이후의 전환 경로: 웹 방문자 → (앱 설치? 재방문? 공유?) 중 무엇을 KPI로 삼는가.
  - 측정 계획: 무엇을 언제부터 재야 "유입이 늘었다"를 반증 가능하게 말할 수 있는가.
- 산출: URL 설계 · 메타데이터/구조화 데이터 방침 · 사이트맵 전략 · KPI 3개 이하.
- 주의: 기존 `site/`(Jekyll)와 도메인·경로가 충돌하거나 중복 콘텐츠가 되지 않게 하라.

#### 페르소나 2 — 웹 프론트엔드 아키텍트 (React)
- 판정할 것:
  - **렌더링 전략**: SSG / ISR / SSR / CSR 중 무엇을, 어느 화면에? 650개 용어는 빌드 타임 정적 생성이 가능한 규모다 — 이 사실을 활용하라.
  - **프레임워크**: Next.js / Remix / Astro(+React 아일랜드) / Vite SPA. 페르소나 1의 SEO 요구와 1인 유지보수 비용 양쪽으로 채점해 **하나를 고르고 나머지를 기각하라.**
  - **호스팅**: 백엔드가 이미 Cloudflare Worker이므로 Cloudflare Pages/Workers 정합성을 우선 검토하되, 맹목적으로 따르지는 마라.
  - 상태 관리: 현재 `StateFlow` 기반 단방향 흐름을 웹에서 어떤 형태로 재현할지 (서버 상태 vs 클라 상태 분리).
  - 디자인 자산 상속: `docs/design` 토큰과 DM 폰트 3종을 웹 디자인 시스템으로 어떻게 옮기는가. **새로 디자인하지 말고 상속하라** — 이미 App Store에 나간 시각 정체성이 있다.
  - 접근성·Core Web Vitals 기준선.
- 산출: 프레임워크 결정 + 기각 사유 · 라우팅/렌더링 표 · 디렉토리 구조 초안.

#### 페르소나 3 — KMP 자산 이식 감정관
> 6,330줄 중 **무엇이 살고 무엇이 죽는지**를 냉정하게 판정하는 사람. 재사용률을 부풀리지 마라.

- 판정할 것:
  - 파일/레이어 단위 이식 판정표: `이식 가능(로직 번역) / 재작성 / 폐기 / 웹에 불필요` 4분류.
    - Compose UI 7화면 — 재작성이 불가피한가?
    - ViewModel 4종의 **상태 기계와 엣지 케이스**(디바운스 300ms, 최근검색 5개 한도, 에러 종류 `ErrorKind`, 로딩 표현)는 코드가 아니라 **명세로 이식**되어야 한다. 그 명세를 어디서 뽑을 것인가.
    - `TermRepository`의 4단 폴백 정책 — 웹에서 몇 단이 남는가?
    - SQLDelight → 웹 저장소(IndexedDB / localStorage) 대응.
    - Ktor Client → `fetch`. `AppJson`/`kotlinx.serialization` 스키마 → TypeScript 타입.
  - **Kotlin/Wasm(CMP 웹 타깃) 대안을 명시적으로 다뤄라.** 같은 코드베이스로 웹을 낼 수 있다는 유혹이 있다. 하지만 CMP 웹은 캔버스 렌더링이라 DOM이 없고 — 즉 **이 이행의 1차 목적인 SEO 유입에 정면으로 반한다.** 채택/기각 판정을 근거와 함께 문서에 남겨라. (기각한다면 그 사실 자체가 "왜 React인가"의 답이 된다.)
  - 테스트 자산: `commonTest`의 계약 테스트(예: `normalizeKeyword` 동치, `ClaudeApiTest`)를 웹에서 어떻게 등가로 보존하는가. **동일 입력 → 동일 출력**을 보장할 골든 케이스 세트를 지정하라.
- 산출: 이식 판정표 · Kotlin/Wasm 채택 여부 결정문 · 웹으로 넘겨야 할 "숨은 규칙" 목록.

#### 페르소나 4 — 백엔드 경계·남용 방지 담당
> **이 설계에서 가장 위험한 자리다.** 여기가 틀리면 요금 청구서로 실패한다.

- 판정할 것:
  - 현재 한도 모델은 `X-Device-Id` 헤더 기반 **기기당 일 10회**다. 브라우저에서 이 헤더는 **클라이언트가 자유롭게 위조·리셋 가능**하다 (시크릿 창, 로컬스토리지 삭제, curl). 즉 **웹에 AI 폴백을 그대로 열면 Anthropic 비용이 익명 트래픽에 무방비로 노출된다.**
  - 이 문제에 대해 최소 3개 안을 제시하고 하나를 고르라. 예: 웹에서 AI 폴백 차단(정적 650개만) / Turnstile 등 사람 검증 / 계정+쿼터 / 서버 측 IP·ASN 한도 / 캐시 히트만 허용하고 신규 생성은 앱 전용.
  - **CORS**: 현재 프록시는 앱 클라이언트만 상정한다. 브라우저 Origin 허용 정책을 어떻게 바꾸는가. 이는 `devetym-proxy` repo 변경을 의미하며, INV-1("앱 코드 무변경")을 깨지 않는지 확인하라.
  - D1 캐시를 웹이 **읽기 전용**으로 쓰는 경로가 성립하는가 — 그게 성립하면 비용 노출 없이 콘텐츠를 넓힐 수 있다.
  - 비용 상한(월 예산)과 그 상한을 물리적으로 강제하는 장치.
- 산출: 남용 위협 모델 · 채택안 1개 + 기각안들 · `devetym-proxy` 변경 범위 · 비용 시나리오 (정상 / 봇 폭주 / 바이럴).

#### 페르소나 5 — 제품 범위·정본 조정자
- 판정할 것:
  - §1의 갈림길 답변을 받아 **범위를 못 박는다.** 웹 v1에 들어갈 화면과 안 들어갈 화면을 목록으로 확정.
  - 1인 개발자의 **이중 유지보수 비용** — 용어 하나 추가할 때 몇 곳을 고쳐야 하는가? 그 수를 1로 만드는 구조를 제안하라.
  - 앱과 웹이 공존할 경우의 **정본 문서 배치**: 새 repo인가 이 repo의 하위 디렉토리인가. `ROADMAP.md`·ADR과의 관계. **새 ADR이 필요한 결정이 무엇인지 지목하라** (예: 웹 프레임워크 선택, 웹 AI 폴백 정책).
  - 마일스톤 분할: 유입 목표에 **가장 빨리 도달하는 최소 슬라이스**를 W1로 잡아라. (힌트: 검색 유입은 "650개 정적 페이지 + 사이트맵"만으로도 발생하기 시작한다 — 개인화 기능은 그 뒤여도 된다.)
  - 이 저장소의 기존 규율 준수: 진행 상태는 로드맵/핸드오프(디스크)가 정본, 프롬프트성 문서는 `🤖-` 접두, 이슈는 GitHub Issues.
- 산출: 웹 v1 범위표(포함/제외) · 마일스톤 W1~Wn · 필요 ADR 목록 · 문서 배치안.

#### 페르소나 6 — 적대적 검수자 (Red Team)
> 위 다섯 명이 결론을 낸 **뒤에** 발언한다. 동의가 아니라 반증이 임무다.

- 할 것:
  - 각 결정에 대해 **"이게 틀렸다면 어떤 증거로 드러나는가"**를 쓰라. 반증 불가능한 결정은 결정이 아니라 희망이다.
  - 최소 5개의 실패 모드를 지목하라. 반드시 포함할 후보:
    - 웹을 냈는데 6개월간 검색 유입이 0에 수렴 (콘텐츠가 얇거나, 색인이 안 되거나, 검색 수요 자체가 없음)
    - AI 폴백 남용으로 첫 달 요금 폭발
    - 앱과 웹의 용어 콘텐츠가 갈라져 같은 단어에 다른 설명이 뜸
    - 1인 유지보수 한계로 웹이 반쯤 만들어진 채 방치 → 앱 트랙까지 정체
    - 이미 게시된 iOS 앱의 사용자 경험 퇴행 (프록시 정책 변경 부작용)
  - 이 프로젝트가 실제로 겪은 패턴을 근거로 삼아라: **"빌드는 되는데 실기동은 깨진다"** 류의 갭이 마일스톤마다 재발했다. 웹에서 이에 대응하는 갭이 무엇인지 지목하라 (예: 로컬 dev 서버는 되는데 정적 빌드/색인은 안 되는 경우).
  - 마지막으로: **"이 이행을 하지 않는 것"이 더 나은 시나리오**가 존재하는지 검토하라. 예컨대 앱을 유지한 채 `site/`를 콘텐츠 사이트로 키우는 것만으로 유입 목적이 달성된다면, React 웹앱은 과잉일 수 있다. 진지하게 다뤄라.

### 3. 진행 순서

1. **라운드 0** — 저장소를 직접 읽어 §0 사실 정본을 검증한다. 어긋난 게 있으면 먼저 보고하라.
2. **라운드 1** — §1 갈림길 4개를 추천안과 함께 사용자에게 확인받는다. 여기서 멈추고 답을 기다려라.
3. **라운드 2** — 페르소나 1~5가 각자 섹션으로 판정한다. 서로 충돌하는 결론은 숨기지 말고 충돌인 채로 드러낸 뒤 조정자(페르소나 5)가 중재한다.
4. **라운드 3** — 페르소나 6이 반증한다. 반증으로 무너진 결정은 라운드 2로 되돌린다.
5. **라운드 4** — 설계서를 확정 산출한다.

### 4. 산출물 요구사항

- 형식: 마크다운 설계서 1편. 사람이 읽는 문서이므로 `🤖` 접두를 붙이지 않는다.
- 반드시 포함:
  - 결정표 — 각 행: `결정 / 채택안 / 기각안 / 근거 / 뒤집힐 조건`
  - 이식 판정표 (페르소나 3)
  - 남용 위협 모델 + 비용 시나리오 (페르소나 4)
  - 웹 v1 범위표 + 마일스톤 (페르소나 5)
  - 실패 모드 5개 + 각각의 조기 경보 신호 (페르소나 6)
  - 열린 질문 목록 — 사람이 답해야 하는 것
- 금지:
  - 코드 작성 (스니펫은 개념 설명에 필요한 최소한만)
  - `~/devetym` 파일 수정 — 설계 단계에서는 읽기만 한다
  - 확인하지 않은 라이브러리 버전·API 단정 (최신 프레임워크 상황은 필요하면 검색해 확인하라)
  - "재사용률 80%" 같은 근거 없는 낙관 수치

## (프롬프트 끝)

### 이 프롬프트를 쓰는 사람에게

- 라운드 1에서 프롬프트가 멈추고 질문을 던지는 건 **정상 동작**이다. 특히 §1-1(앱의 운명)은 네가 답해야 설계가 진행된다.
- 페르소나 6이 "이행하지 마라"고 결론 내는 것도 유효한 산출이다. 그 경우 근거를 보고 판단하면 된다.
- 설계서가 나온 뒤 구현 프롬프트가 따로 필요하면, 확정된 설계서를 정본으로 삼아 별도 `🤖-` 핸드오프를 만든다.
