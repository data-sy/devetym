웹을 「크게」 짓기로 했습니다

3주간 열려 있던 질문 — "웹을 얼마나 크게 만드나" — 를 오늘 닫았습니다. 답은 가장 큰 형태입니다: 용어 650개를 전부 웹페이지로 펼치고, 웹에서도 AI가 답합니다. 그 결정이 요구하던 규범 3건도 함께 비준해, 착수를 막는 것은 이제 도메인 구매 하나뿐입니다.

콘텐츠 자산650 용어한글 별칭 1,097개 동봉
오늘의 결정「크게」650장 + 웹 AI
월 비용 상한$303층 캡 + 계정 하드 리밋
완성까지3~4주도메인 구매 시점부터

01무엇을 정했나

선택지는 셋이었습니다. 같은 콘텐츠를 얼마나 넓게 펼치고, AI를 웹에서도 여느냐가 갈랐습니다.

선택지형태검색 자산기간이 안의 약점
작게소개 페이지 3~5장0장즉시키우려면 사실상 다시 만듦
중간650장 읽기 전용650장1~2주웹에 제품의 핵심(AI)이 없음
크게650장 + 웹에서도 AI 답변650장3~4주비용 면이 열림 → 상한으로 막음(03)
고른 이유는 수요 데이터가 아니라 구조입니다

제품의 정체는 "무엇을 물어도 어원을 설명해준다"입니다. 「중간」은 그 정체가 빠진 웹이고, 어차피 「크게」로 승급할 예정이었습니다 — 즉 지나갈 중간역에 승급 비용만 내는 선택이었습니다. 그래서 한 번에 갑니다.

그 대가로 반나절짜리 시장 실측을 취소했습니다

준비돼 있던 검색 수요 조사(광고 도구로 표본 24개 조회)는 「중간 vs 작게」를 가르는 장치였습니다. 「크게」를 고른 순간 그 갈림길이 사라져 조사도 의미를 잃습니다. 폐기가 아니라 보관 — 되살릴 일이 생기면 그대로 씁니다.

02웹이 여는 것 — 왜 650장이 자산인가

앱은 내려받아야 내용이 보입니다. 검색 결과에도, 커뮤니티 링크에도 착지할 면이 없습니다. 웹은 그 두 개의 유입 경로를 동시에 엽니다.

유입 경로웹이 하는 일검증 상태
검색(SEO)용어 하나당 페이지 하나. 650개 표제어 + 한글 별칭 1,097개가 색인 대상미검증 — 04 참조
커뮤니티 씨딩기술 커뮤니티 게시글의 착지면. 클릭하면 설치 없이 내용이 보임검색 수요와 무관하게 성립
AI 시연사전에 없는 단어를 웹에서 즉석 생성 — 무한 커버리지를 첫 방문에 증명앱에서 이미 작동 중

씨딩 게시글은 이미 작성돼 있고 웹 완성과 동시에 발사하도록 묶여 있습니다. 즉 웹은 마케팅의 선행 조건이기도 합니다.

03돈이 새지 않는 구조

웹에 AI를 여는 결정의 유일한 실질 위험은 비용입니다. 방어는 취향이 아니라 배포 순서로 강제돼 있습니다 — 방어(W1a)를 먼저 배포하고, 그 다음에 웹을 엽니다(W1b).

층무엇을 막나값성격
사용자 대면브라우저 1인당 AI 신규 생성3건/일UX 한도 겸 앱 유도 전환점
남용 방지IP 단위 백스톱(한도 리셋 우회)15건/일모바일 공용 IP 감안
예산웹 전역 합산30건/일비용 상한
계정모든 경로 합산 지출$30/월공급사 측 하드 리밋

중요한 회계 사실: 저 한도는 "아무도 물어본 적 없는 새 단어"에만 걸립니다. 650개 사전과 이미 생성된 답변은 캐시에서 나가므로 비용도 한도 소모도 0입니다. 그리고 새 단어 비율은 시간이 갈수록 단조 감소합니다 — 한 번 만든 답은 영구 자산이 되고, 자주 찾는 항목은 앱 번들로 승격됩니다.

한도가 곧 전환 장치입니다

웹에서 3건을 쓴 방문자는 이미 적극 사용자입니다. 그 지점에서 "무제한은 앱에서"를 전면에 세웁니다 — 이 프로젝트에서 유일하게 측정 가능한 전환 경로이고, 그래서 KPI가 여기서 나옵니다. 웹은 능력을 증명하고, 앱이 무제한 제공합니다.

04정직하게 남는 위험 셋

미검증 전제 한국 개발자가 한국어로 어원을 검색하는가 한 번도 확인한 적 없습니다. 오늘 그 확인을 사후로 미루기로 결정했습니다 — 위험을 없앤 게 아니라 눈 뜨고 받아들인 것입니다. 완충 — 웹의 값이 검색 단독에 걸려 있지 않습니다(씨딩 착지면·AI 시연). 판정 — 배포 8주 후 실측(색인률·유입)으로 사후 채점.
콘텐츠 리스크 표제어가 전부 영어, 본문 절반이 짧다 650개 표제어에 한글이 0개이고 한국어 이름은 앱 안에만 있습니다. 본문은 317개(48.8%)가 300자 미만입니다. 대응 — 한글 별칭 1,097개를 제목·본문 첫 줄에 1급으로 승격(선택 아닌 필수). 짧은 문서는 카테고리 허브·관련 용어로 두께를 만듦.
기존 제품 보호 웹 트래픽이 앱 사용자를 밀어내면 안 된다 웹과 앱이 같은 백엔드를 씁니다. 방어 없이 열면 웹 폭주가 이미 게시된 앱의 사용자를 막을 수 있습니다. 대응 — 한도를 표면별로 분리하고, 요청에 표면 태그를 붙여 앱 영향도를 관측 가능하게 만든 뒤에야 웹을 엽니다.

05일정 — 도메인 구매 시점부터 3~4주

✅ 완료규모 결정 + 규범 3건 비준스택·비용 경계·프롬프트 소유권을 오늘 못 박음2026-08-25
⬜ 게이트devetym.com 구매돈·계정이 필요해 사람만 할 수 있음 — 유일한 차단 요인사람
W0기반DNS 연결 · 검색엔진 소유권 확인 · 앱 디자인 토큰을 웹으로 추출~3일
W1a방어 먼저표면 분리 한도 · 봇 차단 · 프롬프트를 서버 정본으로 이전~1주
W1b웹 본체 공개650장 + 검색 + AI 답변 + 사이트맵 제출~1.5주
W2색인 확장카테고리 허브 · 구조화 데이터 · 짧은 문서 보강 → 씨딩 발사~1주
W3채점8주 실측 — 색인률·유입·앱 전환. 04의 미검증 전제가 여기서 판정됨+8주
완료 기준은 "빌드 성공"이 아닙니다

이 프로젝트는 마일스톤마다 "빌드는 되는데 실기기에서 깨진다"를 겪었습니다. 웹의 대응물은 "빌드는 되는데 색인은 안 된다"입니다. 그래서 완료 오라클을 배포된 실제 URL 650개 전수 응답 확인 + 검색엔진 실측으로 고정했습니다.

06오늘 세션이 남긴 것

✓규모 판정 종결 — 「크게」. 3주간 열려 있던 유일한 사람 판정 항목
✓규범 3건 비준 — 프레임워크·렌더링 경계 / 웹 AI 남용 방지 경계 / 프롬프트 소유권 이전. 모두 제안 → 채택
✓미결 질문 2건 종결 — 프롬프트 서버 이전 시점(=방어 단계에 포함) · 한도 화면 방향(=앱 유도 전면)
✓취소된 작업 보관 — 검색 수요 실측 런북을 아카이브로. 취소 사유를 함께 기록
✓복귀 경로 갱신 — 맥락을 다 잊고 돌아와도 운영 문서만 읽으면 현재 상태로 복귀 가능
지금 필요한 것은 하나입니다

devetym.com 구매(2026-08-25 기준 미등록 확인). 그 외 모든 단계는 승인 없이 진행됩니다. 도메인 없이도 임시 주소로 개발은 시작할 수 있으나, 검색엔진 소유권 확인과 색인 측정은 실제 도메인이 있어야 합니다.

단, 앱의 개인정보 방침 주소는 마지막에 바꿉니다

현재 게시된 iOS 앱이 여는 라이브 주소이고 스토어 등록 정보와 일치해야 합니다. ① 구매 → ② 새 도메인에 방침 페이지 실제 게시·응답 확인 → ③ 앱 상수 교체 → ④ 스토어 라벨 갱신. 순서를 뒤집으면 게시된 앱이 죽은 주소를 가리킵니다.
